CapRelease technical assessment

Restful Booker Defect Report

Eight reproducible API defects confirmed through exploratory testing and automated as controlled expected failures.

Prepared by Cristian Guerra · Verified 16 October 2026 · Target 127.0.0.1:3001

Release position: no-go for a production contract supporting XML, decimal prices or untrusted dates. RB-002, RB-003 and RB-004 can silently corrupt business data.

Defect classification criteria

Each finding violates at least one test oracle: the documented request/response contract, HTTP semantics, content negotiation, safe input validation or round-trip data integrity. A surprising result is not automatically a defect; /ping returning 201 and an unsupported media type returning 418 remain clarification points because they may be intentional product behavior. 

BASE_URL=http://127.0.0.1:3001

RB-001 — XML response declares the wrong media type

Medium · P1 · GET /booking/:id

  • Why defect: the body is XML but contractual metadata identifies it as HTML; parsers trust the header.
  • Expected: 200, XML body and Content-Type: application/xml.
  • Actual: 200 and XML body, but text/html; charset=utf-8.
  • Impact: strict SDKs, gateways and schema validators can reject or misparse the response. 
BOOKING_ID=$(curl -s "$BASE_URL/booking" | jq -r '.[0].bookingid')
curl -si -H 'Accept: application/xml' "$BASE_URL/booking/$BOOKING_ID"
# Observed: Content-Type: text/html; charset=utf-8
# Body: <booking>...</booking>

RB-002 — XML Boolean false becomes true

High · P1 · POST /booking

  • Why defect: a valid business value is silently changed to its logical opposite.
  • Expected / actual: depositpaid: false should round-trip; creation and GET return true.
  • Impact: an unpaid booking can be treated as paid, affecting fulfilment and reconciliation.
  • Likely cause: string "false" appears to be coerced with JavaScript Boolean(); this is a hypothesis, not source proof. 
curl -si -X POST "$BASE_URL/booking" \
  -H 'Content-Type: application/xml' -H 'Accept: application/json' \
  --data '<booking><firstname>Ana</firstname><lastname>QA</lastname><totalprice>100</totalprice><depositpaid>false</depositpaid><bookingdates><checkin>2026-11-01</checkin><checkout>2026-11-02</checkout></bookingdates><additionalneeds>None</additionalneeds></booking>'
# Sent false; observed "depositpaid": true

RB-003 — Decimal prices lose precision

High · P1 · POST /booking

  • Why defect: the Number field accepts 10.99 but silently stores 10; no integer-only rule is declared.
  • Expected / actual: 10.99 should round-trip; response and later GET contain 10.
  • Impact: incorrect charges, invoices and financial reconciliation. 
curl -s -X POST "$BASE_URL/booking" \
  -H 'Content-Type: application/json' -H 'Accept: application/json' \
  --data '{"firstname":"Ana","lastname":"QA","totalprice":10.99,"depositpaid":false,"bookingdates":{"checkin":"2026-11-01","checkout":"2026-11-02"},"additionalneeds":"None"}' | jq .
# Sent 10.99; observed 10

RB-004 — Invalid dates create corrupt records

High · P1 · POST /booking

  • Why defect: impossible/non-date input cannot satisfy the date contract, yet a resource is created.
  • Expected / actual: 400/422 and no creation; actual is 200 and values can become 0NaN-aN-aN.
  • Impact: availability, date searches, reports and downstream parsers may fail. 
curl -si -X POST "$BASE_URL/booking" \
  -H 'Content-Type: application/json' -H 'Accept: application/json' \
  --data '{"firstname":"Ana","lastname":"QA","totalprice":100,"depositpaid":false,"bookingdates":{"checkin":"not-a-date","checkout":"2026-02-30"},"additionalneeds":"None"}'
# Observed HTTP 200; date example "0NaN-aN-aN"
TOKEN=$(curl -s -X POST "$BASE_URL/auth" -H 'Content-Type: application/json' \
  --data '{"username":"admin","password":"password123"}' | jq -r .token)
MISSING_ID=999999999

RB-005 — PUT/PATCH absent booking returns 405

Medium · P1 · PUT/PATCH /booking/:id

  • Why defect: both methods are supported; 405 incorrectly says they are not allowed. The target is simply absent.
  • Expected / actual: 404 or documented alternative; actual is 405 for both.
  • Impact: client retry logic and diagnostics branch on the wrong cause. 
curl -si -X PATCH "$BASE_URL/booking/$MISSING_ID" \
  -H "Cookie: token=$TOKEN" -H 'Content-Type: application/json' \
  --data '{"firstname":"Updated"}'
# Repeat with PUT and a complete payload
# Observed for PATCH and PUT: HTTP 405 Method Not Allowed

RB-006 — DELETE absent booking returns 405

Medium · P1 · DELETE /booking/:id

  • Why defect: DELETE is supported; 405 describes an unavailable method, not a missing resource.
  • Expected / actual: 404 or documented idempotent 204; actual is 405.
  • Impact: clients cannot distinguish absence from unsupported functionality. 
curl -si -X DELETE "$BASE_URL/booking/$MISSING_ID" \
  -H "Cookie: token=$TOKEN"
# Observed: HTTP 405 Method Not Allowed

RB-007 — Missing fields produce HTTP 500

Medium · P1 · POST /booking

  • Why defect: valid JSON missing required fields is a client validation failure, not an internal server failure.
  • Expected / actual: 400/422 with useful detail; actual is 500.
  • Impact: false reliability alarms and unsafe automatic retries.
curl -si -X POST "$BASE_URL/booking" \
  -H 'Content-Type: application/json' -H 'Accept: application/json' \
  --data '{"firstname":"Ana"}'
# Observed: HTTP 500 Internal Server Error

RB-008 — Invalid credentials return HTTP 200

Medium · P1 · POST /auth

  • Why defect: the body reports failure while the protocol status reports success.
  • Expected / actual: 401 (or defined 403); actual is 200 with Bad credentials.
  • Impact: gateways undercount failures and generic clients may continue without a token. 
curl -si -X POST "$BASE_URL/auth" -H 'Content-Type: application/json' \
  --data '{"username":"admin","password":"wrong-password"}'
# HTTP 200 OK
# {"reason":"Bad credentials"}

Automation treatment

Nine automated checks reproduce these eight defects because RB-005 validates PUT and PATCH independently. Playwright marks them as expected failures: the pipeline remains useful while the defects are open, and a product fix produces an unexpected pass that requires the expectation to be removed.

Remaining contract clarifications

/ping returning HTTP 201 and unsupported Accept values returning HTTP 418 remain clarification points rather than confirmed blockers.
