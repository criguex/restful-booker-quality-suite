Confirmed defect

RB-001 XML response declares the wrong content type

  • Endpoint: GET /booking/:id
  • Request: Accept: application/xml
  • Expected: HTTP 200, XML body and an XML content type.
  • Actual: HTTP 200 and XML body with Content-Type: text/html; charset=utf-8.
  • Impact: Strict clients and schema middleware may reject or misparse the response.
  • Disposition: P1 compatibility defect; fix before XML is advertised as a supported public contract.

Behaviors to clarify with the product team

These observations were not automatically classified as defects because the intended contract needs confirmation:

  • /ping returns 201 rather than the conventional 200.
  • Invalid credentials return HTTP 200 with a reason object.
  • An incomplete create payload returns HTTP 500 rather than a client-side 4xx response.
  • An unsupported Accept value returns the non-standard HTTP 418 response.

Automation design

The framework uses Playwright, TypeScript and Zod. Each test owns uniquely named data and cleans it in finally; no scenario depends on seeded IDs or execution order. Functional, contract and performance checks are separate projects. CI starts a pinned Restful Booker revision in Docker, waits for health, executes static and dynamic gates, and retains reports and traces.

Deliberate exclusions

The live assessment is time-boxed. Load and soak testing, concurrency races, specialist security testing, dependency remediation, browser UI, third-party failure simulation and exhaustive date combinations were left outside the release gate. This keeps the work centered on booking and authorization risk without presenting the assessment as exhaustive coverage.
